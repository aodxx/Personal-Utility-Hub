# Personal Utility Hub — v0.9 Tool Expansion Roadmap

**สถานะเอกสาร:** Planning baseline
**ฐานปัจจุบัน:** v0.8.0, 33 tools (32 public tools), client-side Static PWA
**เป้าหมาย v0.9:** เพิ่มเครื่องมือใหม่อย่างน้อย 20 ตัว และขยายได้ถึง 50 ตัวโดยไม่ทำให้ Tool Registry, Bundle Budget, Offline cache, mobile UX หรือ privacy contract เสื่อมลง

> หลักการของ v0.9 คือ “เพิ่มจำนวนเครื่องมือด้วยระบบ ไม่ใช่เพิ่มความซับซ้อนแบบกระจายตัว” ทุกเครื่องมือใหม่ต้องเป็น module ที่พิสูจน์ได้, lazy-loaded, มี metadata ครบ, มี cleanup ที่ deterministic และผ่าน quality gate ตามประเภทงาน

## 1. เป้าหมายและขอบเขต

จาก baseline ปัจจุบันที่มี 33 tools (32 public tools) การส่งมอบขั้นต่ำ 20 เครื่องมือจะทำให้ catalog มีประมาณ 53 tools ส่วนแผนขยายเต็ม 50 เครื่องมือจะทำให้ catalog มีประมาณ 83 tools ดังนั้น roadmap นี้แบ่งเป็น **Core Expansion 24 tools** ที่ควรส่งมอบใน v0.9 และ **Optional Expansion 16 tools** สำหรับขยายไปสู่เป้าหมาย 50 tools เมื่อ bundle, test runtime และ maintenance capacity ยังอยู่ในงบ

v0.9 ไม่ควรเพิ่ม Backend, telemetry, user account หรือ AI claim ใหม่ การประมวลผลต้องยังอยู่ใน browser และการเก็บข้อมูลผู้ใช้ต้องไม่ขยายเกิน LocalStorage/IndexedDB contract เดิมโดยไม่มี design review และ migration plan

## 2. Guardrails จาก Developer Guide

เครื่องมือทุกตัวต้องเริ่มจาก `src/tools/<tool-id>/metadata.ts` และ `index.ts` จากนั้นลงทะเบียนด้วย dynamic import ใน `src/data/tools.ts` ห้าม import implementation หนักแบบ static จาก App Shell และต้องกำหนด `processing`, `supportsOffline`, `requiresFile`, `status`, `version`, category และ privacy copy ให้ตรง implementation จริง

เครื่องมือ Text/Data ควรเริ่มจาก pure functions และ deterministic export เครื่องมือ Image ต้องควบคุม `ImageBitmap`, object URL, dimensions และ memory เครื่องมือ PDF/File ต้องใช้ lazy `pdf-lib` หรือ PDF.js พร้อม limits เครื่องมือ Audio ต้องต่อกับ shared PCM architecture, Worker/fallback, waveform, preview/export และ cleanup contract เดิม ส่วน category ใหม่ เช่น Video หรือ Archive จะเปิดได้ก็ต่อเมื่อมี privacy boundary, processing architecture และ bundle rationale แยกต่างหาก

ทุก tool ที่มี processing หนักต้องมี empty, loading, processing, cancel, success และ error states รวมถึง TH/EN copy, mobile touch targets, keyboard access และ Offline behavior ตาม metadata ห้ามใช้ข้อความ upload success เป็นหลักฐานว่า processing สำเร็จ ต้องตรวจ result metrics หรือ output state จริง

## 3. Wave plan

| Wave | เป้าหมาย | จำนวนใหม่ | ผลรวมโดยประมาณ | ความเสี่ยง |
|---|---|---:|---:|---|
| Wave 0 | Platform hardening ก่อนเพิ่มจำนวน | 0 | 25 | ป้องกัน registry/test count และ bundle โตแบบควบคุมไม่ได้ |
| Wave 1 | Text/Data และ file utilities ที่ใช้ pure functions | 8 | 33 | ต่ำ |
| Wave 2 | Image batch และ document utilities | 8 | 41 | กลาง |
| Wave 3 | Audio workflow extensions และ media-adjacent tools | 8 | 49 | กลางถึงสูง |
| Wave 4 | Optional scale-out เพื่อแตะ 50 additions | 16 | 65 | สูง; ทำเฉพาะเมื่อ gates ผ่าน |

Wave 1–3 รวม **24 tools** จึงเกินเป้าหมายขั้นต่ำ 20 ตัวโดยไม่ต้องเปิด category ใหม่ ส่วน Wave 4 เป็นรายการสำรอง 16 ตัวสำหรับกรณีที่ทีมต้องการเพิ่มครบ 50 ตัวใน v0.9.x หรือ milestone ถัดไป

## 4. Wave 0 — Platform hardening

ก่อนเพิ่ม tool ใหม่ ควรเปลี่ยน count-based tests ให้ตรวจ registry invariants, category coverage และ metadata contract แทนการแก้ expected count ซ้ำทุกครั้ง ควรเพิ่ม helper สำหรับสร้าง metadata, shared file validation, result status และ test fixtures โดยไม่ทำให้ tool modules ผูกกับ UI implementation มากขึ้น

ควรเพิ่ม bundle report ที่แยก entry, shared runtime, worker chunks และ per-tool lazy chunks พร้อม warning เมื่อ tool ใหม่ import dependency หนักแบบ static ควรเพิ่ม registry lint/check ที่ตรวจ duplicate id/route, missing i18n keys, missing icon asset, missing offline declaration และ missing test ownership

ควรเพิ่ม release checklist template ต่อ wave โดยบันทึก `git diff --check`, typecheck, unit/integration, build, bundle, E2E, audit, Service Worker syntax, GitHub Actions run และ production smoke evidence เสมอ

## 5. Wave 1 — Text/Data and File Utilities: 8 tools

| # | Tool | Category | Input / output | Implementation pattern | Acceptance focus |
|---:|---|---|---|---|---|
| 1 | Markdown Formatter & TOC Builder | Text / Data | Markdown → formatted Markdown/TOC | Pure parser/formatter, no dependency initially | headings, Thai/English, fenced code, duplicate anchors |
| 2 | JSON Schema Inspector | Text / Data | JSON → structure/field report | Lazy or lightweight parser, deterministic report | nested arrays, invalid JSON, large input bounds |
| 3 | YAML ↔ JSON Converter | Text / Data | YAML/JSON ↔ text | Dependency review before adding parser | anchors/unsupported syntax, Unicode, safe errors |
| 4 | Regex Tester & Capture Map | Text / Data | Text + regex → matches/captures | Main-thread pure operation with input limits | invalid regex, zero-width matches, no ReDoS-like unbounded input |
| 5 | URL Query String Builder | Text / Data | URL/query fields ↔ encoded URL | Browser URL APIs, no server call | Unicode, repeated keys, hash/path preservation |
| 6 | JSON Lines Cleaner & Splitter | Text / Data | NDJSON → clean/split JSONL | Streaming-style line processing where possible | malformed line reporting, newline contract, large files |
| 7 | Filename Batch Renamer | File | filename list → rename manifest/ZIP-ready mapping | Local metadata only; no file mutation claim | duplicate names, Unicode normalization, collision preview |
| 8 | File Hash Batch Verifier | PDF / File | multiple files → SHA-256 manifest | Reuse hash Worker and progress/cancel | repeated files, cancellation, deterministic ordering |

Wave 1 ควรเป็น wave ที่เร็วที่สุดและใช้เป็น reference implementation รุ่นใหม่สำหรับ pure text tool, file list tool และ Worker-backed batch tool โดยไม่เพิ่ม dependency ขนาดใหญ่เกินจำเป็น

## 9. Architecture workstreams

### Registry and metadata

กำหนด `ToolDefinition` หรือ shared metadata helper เฉพาะเมื่อช่วยลด duplication โดยไม่ซ่อน semantics สำคัญ ทุก entry ต้องมี unique id/route, category, lazy loader, icon, bilingual copy, privacy declaration, offline decision และ version ที่อธิบายได้ ควรสร้าง script ตรวจ duplicate route, missing translation และ missing visual asset ก่อน test suite

### Processing layer

Pure functions ต้องอยู่ใน `src/core` หรือ processing-specific module ไม่อยู่ใน `index.ts` หากงานใช้เวลานานให้เพิ่ม operation typed union ใน `processing-client.ts` และ `processing.worker.ts` พร้อม cloned transferables, progress, cancellation, error normalization และ deterministic fallback ก่อนสร้าง UI ใหม่

### Shared UI primitives

ควรขยาย shared workbench ตาม semantics ไม่ใช่สร้าง mega-component ที่มี condition ทุก tool สำหรับ Image/PDF/Audio ให้ shared layer รับเฉพาะ lifecycle, preview/result, cleanup และ progress primitives ขณะที่ controls, validation และ output semantics อยู่ใน tool เอง

### Offline and PWA

ทุก wave ต้องตัดสินใจ `supportsOffline` อย่าง explicit และใช้ `prepareOffline` เฉพาะ asset ที่จำเป็นจริง ควรตรวจ cache growth, stale cache invalidation และ offline-open contract ต่อ wave ไม่ควร pre-cache ทุก lazy chunk ไว้ใน App Shell

## 10. Testing and release gates

ก่อนเปลี่ยน tool เป็น `active` ต้องผ่าน gate ตามนี้:

| Gate | Minimum requirement |
|---|---|
| Contract | `metadata.ts`/`index.ts`, unique id/route, lazy registry, bilingual copy, privacy fields |
| Pure tests | happy path, invalid input, bounds, Unicode/locale หรือ binary header ตามประเภท |
| Integration | lazy load, metadata identity, category/search, offline flag และ cleanup ownership |
| E2E | upload/input → configure → process → Preview → Export/Download → result verification |
| Mobile | 360 × 740 และ Pixel 7 class, no horizontal overflow, touch/keyboard accessibility |
| Heavy processing | Worker path, fallback path, progress, cancel, repeated operation และ resource cleanup |
| Release | typecheck, unit, build, bundle budget, audit, SW syntax, git diff check |
| Production | GitHub Actions green on HEAD, Pages deploy, production route/search/settings smoke และ offline evidence |

ควรใช้ **representative E2E sampling** ต่อ wave เพื่อไม่ให้ 50 tools ทำให้ test runtime โตแบบเส้นตรงเกินไป แต่ทุก tool ต้องมีอย่างน้อย route/metadata lazy-load coverage และ pure/integration tests ที่ตรงกับ risk ของตนเอง เครื่องมือ processing-heavy ต้องมี browser workflow จริง ไม่ใช่เพียง snapshot หรือข้อความ success

## 11. Bundle, performance และ maintenance budget

ก่อนเริ่ม v0.9 ให้คงเกณฑ์ v0.8 เป็น hard ceiling: Entry gzip ≤45 KB, largest lazy chunk ≤900 KB และ JavaScript รวม gzip ≤1,600 KB หากเพิ่ม dependency ใหม่ต้องวัดผลทั้ง entry, shared chunk, worker chunk และ cold-load route ไม่ดูเฉพาะขนาดของ tool chunk

แนะนำให้แบ่ง batch release เป็น 4–6 tools ต่อ pull request และไม่รวมหลาย category ที่มี dependency หนักใน PR เดียว การ merge แต่ละครั้งควรสร้าง evidence สั้น ๆ ว่า catalog count, bundle metrics, test count, cache version และ production smoke เปลี่ยนอย่างไร

## 13. Definition of Done สำหรับ v0.9

v0.9 พร้อมประกาศเมื่อมีเครื่องมือใหม่อย่างน้อย 20 ตัวที่ active จริงและผ่าน contract, tests, build, bundle, CI และ production smoke ตาม risk profile โดย catalog รวมไม่น้อยกว่า 45 tools แต่ไม่มี count assertion ที่เปราะบางเกินความจำเป็น

เอกสาร `README.md`, `PROGRESS.md`, `TEST_REPORT.md` และ `docs/ADDING_A_TOOL.md` ต้องอัปเดตจาก source จริง มี release version/cache identifiers ชุดเดียวกัน และอธิบาย known limitations อย่างตรงไปตรงมา ต้องไม่มี debug/temp artifacts, ไม่มี user schema break, ไม่มี backend/telemetry ใหม่โดยไม่ได้รับการออกแบบ และต้องชี้ไปยัง GitHub Actions run บน final HEAD

## 14. กลยุทธ์แนะนำ

ไม่ควรตั้งเป้า “50 tools ใน release เดียว” เป็น acceptance criterion หลัก ควรตั้งเป้า **20 tools ที่มีคุณภาพและทำให้ต้นทุนการเพิ่ม tool ตัวที่ 21 ต่ำลง** ก่อน เมื่อ registry checks, shared processing primitives และ evidence pipeline แข็งแรงแล้ว การขยายจาก 20 ไป 50 จะเป็นงานซ้ำตามระบบมากกว่างานเสี่ยงแบบ bespoke

ลำดับที่แนะนำคือ Text/Data ก่อนเพื่อสร้าง reference patterns, Image/PDF ถัดมาเพื่อพิสูจน์ memory/Worker discipline และ Audio หลังจาก production process/export ของ v0.8 มีหลักฐานสมบูรณ์ การเปิด category Video หรือ Archive ควรเลื่อนไปหลัง v0.9 เพราะมี codec, memory, browser compatibility และ bundle risk สูงกว่าการขยาย taxonomy เดิม
